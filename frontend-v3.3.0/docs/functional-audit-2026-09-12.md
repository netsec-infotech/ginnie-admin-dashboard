# Functional audit — 12 September 2026

The repository received a broad automated audit and a targeted review of customer flows. Concrete defects were fixed in checkout, session restoration and cleanup, notifications, Stories, translations, and production/PWA builds. This is not a claim that every runtime path works: a fresh headless Chrome profile covered public and guest pages, while payments, authenticated backend mutations, native device capabilities, and deployed infrastructure were not exercised end to end.

**Scope and method.** Inventoried 405 TypeScript/TSX source files and 42 page templates, including the two Next framework pages (40 routable templates). Ran the complete Vitest suite, TypeScript, ESLint, dependency audit, static-export build and SEO checks. Reviewed shared authentication, API failure handling, checkout/payment adapters, order actions, support behavior, notifications, persistence, and build scripts. The inventory is not line-by-line coverage of all 405 files; no statement-coverage percentage was measured.

**Open findings needing integration or product decisions.**

1. **Payment confirmation:** Wallet handlers in `src/components/PaymentGateway/Stripe.tsx`, `RazorPay.tsx`, and `Paystack.tsx` construct a successful result after a provider callback without a frontend request confirming backend credit. Stripe also continues when a PaymentIntent exists without checking its status. These are confirmed client-code behaviors, not proof that the backend credits money incorrectly. Validate backend confirmation, retry idempotency, and delayed-payment reconciliation in each gateway sandbox.
2. **Payment return handling:** Stripe can redirect to the orders/wallet page before the subsequent client `handleCheckout` path executes. Verify that backend webhooks or return handling complete such orders. No provider transaction or webhook was executed during this audit.
3. **Guest account handling:** In the static build, addresses, loyalty points, notifications, orders, referrals, transactions, wallet and wishlists request protected APIs while signed out; several retry HTTP 401 responses. Their account shells still render instead of using a consistent sign-in state. Backend rejection was observed; private data was not returned. Cart/support are guarded, and the tested SSR account routes redirect appropriately. Add a common client guard and gate private fetch/retry behavior.
4. **Google Maps configuration:** The delivery-zone map displayed the provider failure screen and raised an unhandled `getRootNode` error during the broad static browser run. A focused recheck on a localhost test origin reported `RefererNotAllowedMapError`. Configure the allowed development/production referrers for the Maps key and retest map loading, teardown and tracking. This local-origin failure does not establish that the configured production domain fails.
5. **Static-hosting network failures:** Nonblocking HTTP 404s occurred for `/_vercel/speed-insights/script.js`, `/favicon.ico`, and `/_next/data/<build-id>/index.json` during guest-cart redirection. The redirect ultimately reached the homepage. SpeedInsights is mounted unconditionally in `src/layouts/default.tsx`; the data request needs review against conditional SSR exports and deployed static routing. The local HTTP server served exported files and did not emulate Apache rewrite rules.
6. **Backend availability:** Public catalog endpoints intermittently returned HTTP 500 during static generation, including store details and delivery-zone products. Existing retries recovered, the static and SSR builds completed, and direct rechecks of store details and web settings returned HTTP 200 with `success: true`. Availability under build load remains an operational concern.
7. **Support session rules:** This frontend repository cannot prove order-support uniqueness or whether a resolved issue should reopen versus create a new session. The backend must enforce the agreed rule under concurrent requests. Existing closed-history/current-chat behavior was not changed during this audit.
8. **Coverage gaps:** There is no complete browser end-to-end suite covering authenticated account, wishlist, wallet, seller-registration and checkout workflows. The smoke test did not submit forms, place orders, validate every interactive control, or measure accessibility comprehensively. Authenticated order details were excluded; order components/helpers were covered by existing tests. Native permissions, push delivery, payment callbacks, and actual offline service-worker upgrades remain unverified.
9. **Section content consistency:** The sampled `/section/649/` page (Top Banners) displayed a count of 1 product alongside No products found. Review whether non-product home-layout sections should have a product-list destination or be excluded from those generated routes. This was a browser observation, not a completed investigation of all section types.
10. **Deployment origin:** Code generation used `http://localhost:3000`. Production canonical URLs, robots/sitemap URLs, response headers, payment return URLs and static rewrite behavior must be checked with deployment configuration. Generated development metadata is not intended for publishing.

Some passing tests emit existing React `act`, mocked-component prop, i18next setup, missing test API environment, or deliberate failure-path warnings. These were not globally suppressed; passing results do not assert a warning-free browser console.

Changes remain local and uncommitted. No deployment, real order/payment/refund, support message, callback request, or outbound message was performed. Generated manifest/robots/sitemap files are restored after validation to avoid publishing audit-environment metadata.

Temporary browser profiles: automatic approval review rejected both scoped and explicit-path deletion attempts with "blocked by policy". Five audit profiles remain under the user Temp directory. Test browsers were closed; audit reports and screenshots are also retained in the task Temp folder.

**Follow-up: newly added product pages.** Reproduced a missing-page failure for a product absent from the static export: ordinary product links already used the live fallback, but `/share/products/:slug/` and its Next navigation JSON explicitly returned 404. Both now use the fallback while preserving existing generated pages, and the product view reads slugs from either URL. Also fixed server-mode blocking generation and revalidation: they searched the permanently cached catalog instead of requesting the current product by slug. Runtime generation now fetches that product directly. Missing products receive a revalidatable 404; transient product API failures throw so ISR can retain an existing page and retry, instead of replacing it with a cached 404.
